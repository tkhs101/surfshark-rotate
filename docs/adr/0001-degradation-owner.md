# ADR 0001：降级决策归脚本所有，不由 mihomo 判定

- 状态：已采纳（2026-10-08）
- 影响范围：`config.yaml` 的 `AUTOFALL` 组、`rotate.py`、`on-mihomo-up.sh`、`install.sh` 能力校验

## 背景

这个项目唯一的目的，是让 `opencode.ai` 的流量每 5 分钟换一个 Surfshark 出口 IP。
为了在私钥到期时不让这个用途彻底停摆，2026-10-07 引入了一条降级链：节点全挂时
`opencode.ai` 自动退到直连，还能用，只是出口变回本机。

用户对该行为的优先级排序非常明确，且不可交换：

> **泄漏本机 GCP 机房 IP 比直接失败更糟。** 失败只是断一次，泄漏是把机房 IP
> 送到对方面前，可能被限流或封禁 —— 而暴露机房 IP 恰恰是这个项目要避免的事。

## 决策

**`AUTOFALL` 从 mihomo 的 `fallback` 组改成 `select` 组，降级与恢复完全由
`rotate.py` 通过 `PUT /proxies/AUTOFALL` 显式切换，内核不参与判断。**

## 为什么不能用 fallback

mihomo `fallback` 的降级判定是**单样本布尔查表**：

- `adapter/outboundgroup/fallback.go` 的 `findAliveProxy()` 顺序遍历成员，
  返回第一个 `AliveForTestUrl()==true` 的
- `Now()` 直接调它，中间没有任何计数器、迟滞或冷却

即「一次探测失败 → 立即降级，一次探测成功 → 立即恢复」。实测（真实内核
v1.19.32）：17 小时内内核自行翻转到 `DIRECT` 共 5 次，其中一次发生在 01:20:25
且当时没有任何轮换在跑，两条 `opencode.ai` 的连接以 `AUTOFALL[DIRECT]` 发出，
即用本机 GCP 机房 IP 出网。

其它看似能救的开关都压不住：

| 手段 | 为什么不行 |
|---|---|
| `max-failed-times` | 只作用于 `onDialFailed`（拨号失败路径），周期健康检查根本不走它。照抄会得到「以为防住了其实没防住」 |
| `fixed`（钉选成员） | `findAliveProxy` 仍检查存活，钉选只是「优先选谁」 |
| `relay` 组 | 已被移除 |
| `fallback-filter` | 是 DNS 字段，不是代理组 |
| 调 `timeout` / `interval` | 只能在「假降级」与「真降级变慢」之间换，消不掉 |

**结论：任何配置开关都给 `fallback` 加不上去抖。** 单样本在原理上也无法区分
「瞬时抖动」和「真死」。

`select` 组没有健康检查，**永不自行翻转**。降级只可能由脚本的一次显式调用造成。

## 判据

| 方向 | 判据 | 理由 |
|---|---|---|
| 降级 | 连续 2 轮取不到出口 IP，**且**控制面 `/proxies/<节点>/delay` 对**全部**探针端点都探测不到 | 只看探测失败会把「ip.sb 挂了」误当成「隧道坏了」，那是新的泄漏源。隧道好着就不该降级 |
| 恢复 | 连续 2 次控制面探测健康（**任一**探针端点响应即算该次健康） | 单次侥幸成功不足以证明修好了 —— 打通的只是探针站点，不是我们要保的出口 |

两边都是「连续两次」，迟滞对称，避免反复降级/恢复的抖动。

## 副作用与已知残余风险

- **脚本成为唯一决策方，因此脚本失效 = 不会降级**（fail-closed）。方向上比泄漏
  安全，但这是一个新的失效模式：rotate.py 坏掉时 opencode.ai 会一直连不上而
  没有降级横幅。`status.sh` 的 `ExecMainStatus` 仍会标红。
- **降级确认从最快 60 秒变为约 10 分钟。** 对「持续数天」的密钥过期无影响。
- **脚本确认降级后的那一瞬间仍会直连** —— 那正是要保留的行为，无法消除。
- **恢复路径有两条**：换私钥 + `restart mihomo` 走钩子；手工跑一轮 `rotate.py`
  走函数内分支。后者钩子不触发，所以 `clear_degraded()` 会主动
  `systemctl start` 把定时器启回来。

## 状态文件的归属

状态文件有两个写入方。**schema 的 owner 是 `rotate.py`**，钩子通过
`rotate.py --clear-degraded` / `--recheck-tried` / `--reset-recheck` 修改状态，
不再自带一份 key 列表。`status.sh` 是第三个读取方。

写盘三道防线：`os.replace`（同文件系统原子改名）+ `fsync` 父目录
（否则断电后改名可能回退，而「旧内容」恰好是最坏的内容）
+ `flock`（**读-改-写全程**都在临界区内）。

写入统一走 `update_state(patch, remove, incr, require_existing)`：

- `patch` 只写它列出的键，`remove` 只删它列出的键 —— 调用方传整份快照的做法
  已经制造过事故：合并写会把快照里**这一轮根本没打算改**的过时键也盖回去。
- **`require_existing` 默认 True，即默认不物化**。物化必须显式申请，
  授权点只有两个，都是「本轮真的轮换过了」的证据。
  这条策略来自一个被复现了三次的因果：钩子闸门只看「文件在不在」和
  「有没有 degraded 键」，而一份凭空物化出来的文件**两者都满足** ——
  于是被判成「明确未降级」直接返回，「状态丢失 → 自修」永久失效，
  AUTOFALL 停在 DIRECT 不动。逐个调用方加守卫治不了标，
  因为物化点会不断挪到下一个调用方，必须从策略上关掉。


## 测试夹具与真机的字段一致性（第六轮自查）

`BROAD` 集合曾经写成 config.yaml 的 YAML 拼写，而 mihomo 的 `/rules` 返回的是
CamelCase —— 13 条里 8 条是死的，而测试夹具也用了同样的错拼写，于是全绿。
「替身比真实契约宽松」由此在**上一层**复发：我们从「替换 api()」进化到了
「真起 HTTP 服务」，但伪造的 payload 形状仍然是猜的。

因此专门核了一遍：本项目代码实际读取的字段，与真机返回的是否一致。

  · `/connections` 的 metadata：代码读 `host` / `sniffHost` / `destinationIP`
    —— 三个都真实存在。真机另有 22 个字段（`destinationGeoIP`、`sourceIPASN`、
    `dnsMode`、`specialRules`…）未用。
  · 顶层：代码读 `chains` / `metadata` —— 都存在。
  · `/proxies` 的组：代码读 `all` / `type` —— 真机返回
    `Selector` / `['PROXY','DIRECT']`，与夹具一致。
  · `/rules`：已按真机改为 CamelCase。

**漏掉的更强信号**：真机的 `/connections` 每条连接带 `rule` 与 `rulePayload`，
直接告诉你「命中了哪条规则」。一条 opencode.ai 的连接若 `rule == 'Match'`，
就是确定落进了 `MATCH,DIRECT` —— 比 `chains[0]=='DIRECT'` 更直接，而且能区分
两种泄漏原因（sniffer 失效 vs 配置被改坏），排查方向不同。
本轮未采用：它仍需先判定该连接属于 opencode.ai，而那一步依赖域名或 IP，
与现有判据是同一个约束。留作后续。


## 核对点为什么前移，以及它换来了什么代价

分流核对放在**切节点与热重载之前**，规则确认违规就 `raise SystemExit(3)`，
整轮不做任何动作。理由是规则坏着的时候每 5 分钟「切节点 + 热重载
（真的重建 WireGuard 隧道、真的换一次出口 IP）」而 `idx`/`last_ip` 一轮不前进，
系统停在「节点换了但账没记」的状态，且轮换产出在无账可记的情况下静默发生。

前移是安全的：切节点与热重载都**不改**已加载的规则表，`/rules` 只在配置被
重新加载时才变，前后置读到的是同一份，前置的结论不比后置弱。

**代价（此前没有记录，这里补上）**：由于核对在 `reload_config()` **之前**，
磁盘上的 `config.yaml` 若被外部改坏，要到**下一轮**才被发现 ——
本轮核对的是上一轮加载的规则（还是好的）→ 通过 → 随后 `reload_config()`
把坏配置生效 → 泄漏已经发生 → 下一轮才报 VIOLATION。窗口约一轮（5 分钟）。

这个取舍是为了消除「exit 3 时 idx 与实际节点发散」而做的。
如果要消除这个窗口，得把后置核对也留着（两轮都查），代价是多一次 API 调用
（实测 24.8ms，占预算 0.008%）—— 目前判断不划算，因为**窗口期内的泄漏
由 connections 的阳性检测兜着**（它不需要等下一轮，有 opencode.ai 流量时
立刻可见）。若将来不做手动巡检，应重新评估。


## 轮换策略：为什么是「12 小时内不重复」，以及它做不到什么

需求：**12 小时内不重复出口 IP**。

### 旧结构为什么达不到

旧结构是 `TIERS[0] = [JP, KR]` 档内严格交替，而「降档」只在
`new_ip == old_ip`（与上一次**完全相同**）时触发。VPS 实测 48 小时 181 个周期：

  节点分布  JP 90 / KR 91 / **SG 0 / TW 0**
  相邻两次出口 IP 相同  **0 次**
  JP 47 个不同 IP（重复率 48%）· KR 32 个（65%）· 并集 79

所以 `same_ip_streak` 恒为 0、`tier` 恒为 0，**整套分档是死代码**，
而它让人以为「备用节点」是活的 —— 实际上 SG/TW 一次都没启用过。
12 小时 × 5 分钟 = 144 次抽样，而池子只有 79 个地址：数学上必然重复。

### 实测的池（VPS，2026-10-09）

  JP 日本-东京 47 · KR 韩国-首尔 32 · SG 新加坡 17 · **TW 台湾-台北 13**
  并集 = **109**

TW 的 13 来自 2026-10-09 的 24 次连续采样（13 个不同地址，0 次失败）。
它是四个池里**最小**的 —— 也意味着 TW 每 4 轮就要用到一次，
因此它是重摇最频繁的节点。

上一版这里写「TW 未测完，预算按最保守的 15 算」。现在换成实测的 13，
预算反而更紧（见下）。

### 现在的策略

1. **扁平四节点轮询**（不再分档）—— SG/TW 真正进入轮换。
2. **12 小时地址记忆**（`recent`，随状态文件持久化，跨进程）。
3. **撞到窗口内用过的地址就换节点重摇**，最多 8 次。
   **重摇必须换节点**：原地重摇实测接受率 0/9 —— 在同一个池子里抽，
   抽中的必然是用过的。换一个池子抽才解决。
4. **间隔 5 → 10 分钟**，因为 `720 ÷ 间隔 ≤ 池并集`。
   10 分钟需 72 个不同地址，池并集 = **109**，余量 **+51%**。

### 做不到什么（写清楚免得误以为达标了）

  · 这是**概率性**保证，不是硬保证。池子被抽干时仍会重复 ——
    代码会重摇 8 次，仍撞上就**明确说出来**并打出「12h 需要 N 个」
    而不是假装成功。
  · **5 分钟间隔在这个配置下不可行**：144 需要的地址数 > 109 的池并集。
    若哪天实测池子变大，`test_five_minute_interval_is_now_infeasible` 会红，
    那是重新评估的信号。
  · 这 13/47/32/17 是**抽样下界**，不是池子大小的精确值 ——
    24 次抽样只可能低估。所以余量 +51% 是乐观估计。
  · 记忆窗口只有 12 小时；跨更长时间的重复不在这份承诺里。


## 退役触发条件

以下任一成立时应重新审视本决策：

1. mihomo 给代理组增加了可配置的迟滞（连续 N 次失败才切换 / 最短保持时间）。
   届时可考虑把降级交回内核，少一个决策方。
2. 出口 IP 探测换成不依赖第三方 HTTP 服务的方式（例如本地记录隧道对端分配）。
   届时「探测信号 ≠ 隧道死活」的耦合可以消失。
3. mihomo 提供降级事件回调（webhook / 事件订阅），使脚本无需轮询即可获知状态。


## 补充决策：为什么没有采用 `/logs?level=debug` 的 WireGuard 握手信号

调研（2026-10-09）确认 mihomo v1.19.32 **存在**一个完全不依赖第三方 URL 的
隧道存活信号：`GET /logs?level=debug` 会透传 wireguard-go 设备自己的日志，其中
`Received handshake response` / `Receiving keepalive packet` 是与 Surfshark
服务器完成往返的直接证据，`Handshake did not complete... retrying` 是死信号。
对端是 `*.prod.surfshark.com`，与 cp.cloudflare.com / ip.sb 完全解耦。

**仍然不采用**，理由按重要性排序：

1. **它解决的是概率极低的那一类。** 残余风险是「ip.sb 与三个探针端点同时
   失效」导致误降级。要求四个互不相关的外部服务、在同一时刻、对同一个住宅
   出口 IP 同时出问题。
2. **要常驻进程。** `/logs` 是 live-only、无回放（journald 实测 0 条握手日志），
   必须提前挂上订阅才有数据。这会打破本项目「无常驻、纯 systemd 一次性任务」
   的形态，并引入一个新的失效模式：订阅进程自己死了，等于又瞎了，而它的死
   没有任何人会发现。
3. **它的死侧没有运行时证据，且健康侧的实测结果比预想更难用。**

   2026-10-09 实测（生产机订阅 `/logs?level=debug`，样本约 8 分钟）：

   | 信号 | 次数 | 相邻间隔中位 | 范围 |
   |---|---|---|---|
   | `Sending keepalive packet` | 14 | 33.8s | 0 ~ 120s |
   | `Receiving keepalive packet` | 6 | 36.9s | 2.2 ~ 174.6s |
   | `Received handshake response` | 9 | 63.1s | — |
   | `Handshake did not complete` | 0 | — | — |

   周期量级是 30~40 秒，但**抖动很大**：接收侧最坏一次隔了 174.6 秒。
   这意味着「多久没有 keepalive = 死了」的阈值要定在分钟级，
   而它恰恰要被用来判一个**以 5 分钟为周期**的降级决策 ——
   阈值与决策周期几乎同量级，迟滞窗口会被压得很窄。
   要把这个信号接管降级判据，得先有更长窗口（数小时）与死侧对照，
   否则是在拿一个刚够用的信号去替换另一个已经够用的信号。
   死侧（`Handshake did not complete`）至今仍只有二进制字符串证据。

被否掉的另外两条：
  · **只做 SOCKS5 失败分层**：TCP 层超时与「隧道死」签名完全相同，还会被 PMTU 黑洞骗过（SYN 小包过、TLS 证书链丢，探针判健康而真实 HTTPS 全挂）。
    单独上线只是把泄漏概率从「四站点同坏」换成「一站点 TCP 丢包」。
  · **自建探针**（VPS 开端口让出口连回来）：把「三个外部站点」换成了
    「VPS 入口可达性」这一个新的单点，而且出口 IP 一直在换，
    「同一端口来自大量不同 ASN 的连接」看起来就像扫描，
    **被拦概率与轮换频率正相关** —— 探针恰好在系统最正常运转时最不可靠。
    另外它会引入本项目的第一个公网入站监听。

**硬规则（写下来免得以后走错）**：任何一层的失败都不能接到降级上。误判隧道死
会泄漏（本项目头号问题），误判隧道活只是让 opencode.ai 撞一次失败的代理。
层只能加在恢复侧，因为那个方向的错误是安全的。

退役条件仍然是「探测换成不依赖第三方 HTTP 服务」。这条**保持开启**，
等满足以下前提再做：**keepalive 周期与安全阈值已部分达成**（周期实测约 34~37 秒、抖动到 174.6 秒，但仅 8 分钟、6 个样本，不足以定安全阈值）；
仍缺**死侧行为有运行时证据**（只读约束下无法制造握手失败）与**订阅进程的存活可观测**。
