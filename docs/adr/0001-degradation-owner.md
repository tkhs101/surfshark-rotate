# ADR 0001：降级决策归脚本所有，不由 mihomo 判定

- 状态：已采纳（2026-10-08）
- 影响范围：`config.yaml` 的 `AUTOFALL` 组、`rotate.py`、`on-mihomo-up.sh`、`install.sh` 能力校验

## 背景

这个项目唯一的目的，是让 `opencode.ai` 的流量每 5 分钟换一个 Surfshark 出口 IP。
为了在私钥到期时不让这个用途彻底停摆，2026-10-07 引入了一条降级链：节点全挂时
`opencode.ai` 自动退到直连，还能用，只是出口变回本机。

用户对该行为的优先级排序非常明确，且不可交换：

> **泄漏本机 GCP 机房 IP 比直接失败更糟。** 失败只是断一次，泄漏是把机房 IP
> 送到对方面前，可能被限流或封禁 —— 而暴露机房 IP 恰恰是这个项目要避免的事。

## 决策

**`AUTOFALL` 从 mihomo 的 `fallback` 组改成 `select` 组，降级与恢复完全由
`rotate.py` 通过 `PUT /proxies/AUTOFALL` 显式切换，内核不参与判断。**

## 为什么不能用 fallback

mihomo `fallback` 的降级判定是**单样本布尔查表**：

- `adapter/outboundgroup/fallback.go` 的 `findAliveProxy()` 顺序遍历成员，
  返回第一个 `AliveForTestUrl()==true` 的
- `Now()` 直接调它，中间没有任何计数器、迟滞或冷却

即「一次探测失败 → 立即降级，一次探测成功 → 立即恢复」。实测（真实内核
v1.19.32）：17 小时内内核自行翻转到 `DIRECT` 共 5 次，其中一次发生在 01:20:25
且当时没有任何轮换在跑，两条 `opencode.ai` 的连接以 `AUTOFALL[DIRECT]` 发出，
即用本机 GCP 机房 IP 出网。

其它看似能救的开关都压不住：

| 手段 | 为什么不行 |
|---|---|
| `max-failed-times` | 只作用于 `onDialFailed`（拨号失败路径），周期健康检查根本不走它。照抄会得到「以为防住了其实没防住」 |
| `fixed`（钉选成员） | `findAliveProxy` 仍检查存活，钉选只是「优先选谁」 |
| `relay` 组 | 已被移除 |
| `fallback-filter` | 是 DNS 字段，不是代理组 |
| 调 `timeout` / `interval` | 只能在「假降级」与「真降级变慢」之间换，消不掉 |

**结论：任何配置开关都给 `fallback` 加不上去抖。** 单样本在原理上也无法区分
「瞬时抖动」和「真死」。

`select` 组没有健康检查，**永不自行翻转**。降级只可能由脚本的一次显式调用造成。

## 判据

| 方向 | 判据 | 理由 |
|---|---|---|
| 降级 | 连续 2 轮取不到出口 IP，**且**控制面 `/proxies/<节点>/delay` 也探测不到 | 只看探测失败会把「ip.sb 挂了」误当成「隧道坏了」，那是新的泄漏源。隧道好着就不该降级 |
| 恢复 | 连续 2 次控制面探测健康 | 单次侥幸成功不足以证明修好了 —— 探测对象是 `cp.cloudflare.com`，不是我们要保的出口 |

两边都是「连续两次」，迟滞对称，避免反复降级/恢复的抖动。

## 副作用与已知残余风险

- **脚本成为唯一决策方，因此脚本失效 = 不会降级**（fail-closed）。方向上比泄漏
  安全，但这是一个新的失效模式：rotate.py 坏掉时 opencode.ai 会一直连不上而
  没有降级横幅。`status.sh` 的 `ExecMainStatus` 仍会标红。
- **降级确认从最快 60 秒变为约 10 分钟。** 对「持续数天」的密钥过期无影响。
- **脚本确认降级后的那一瞬间仍会直连** —— 那正是要保留的行为，无法消除。
- **恢复路径有两条**：换私钥 + `restart mihomo` 走钩子；手工跑一轮 `rotate.py`
  走函数内分支。后者钩子不触发，所以 `clear_degraded()` 会主动
  `systemctl start` 把定时器启回来。

## 状态文件的归属

状态文件有两个写入方。**schema 的 owner 是 `rotate.py`**，钩子通过
`rotate.py --clear-degraded` 修改状态，不再自带一份 key 列表。

写盘两道防线：`os.replace`（同文件系统原子改名）+ `flock`（读-改-写串行化）。
默认是合并写（只更新显式给出的键），但**删除键必须用 `replace=True`** ——
合并写表达不了删除，否则磁盘上的 `degraded=true` 会被读回来。

## 退役触发条件

以下任一成立时应重新审视本决策：

1. mihomo 给代理组增加了可配置的迟滞（连续 N 次失败才切换 / 最短保持时间）。
   届时可考虑把降级交回内核，少一个决策方。
2. 出口 IP 探测换成不依赖第三方 HTTP 服务的方式（例如本地记录隧道对端分配）。
   届时「探测信号 ≠ 隧道死活」的耦合可以消失。
3. mihomo 提供降级事件回调（webhook / 事件订阅），使脚本无需轮询即可获知状态。
